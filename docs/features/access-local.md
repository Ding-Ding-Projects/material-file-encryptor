# Local access components

`mountAccess(container, services)` mounts the access settings, authenticator registration and local support desk. It returns `destroy()`, `controller`, `load(ids)`, `refreshLocks()`, `openUnlock(id)`, `guard(id, callback, ...args)` and `bind(root)`.

The host supplies `credentialStore` with asynchronous `get`, `set` and `delete` operations backed by its operating-system credential vault. Missing vault access prevents UI registration. Never substitute plaintext settings or browser storage. `dataPath` and `openDataFolder` must reference the same application data directory. The support desk does not delete data or send network requests. `t(key)` may return localized copy, and `notify(message)` receives generic status only. `history.record` receives redacted lock mutation metadata.

## Protection model

Six independent policies cover PIN, password, PIN plus password, password plus TOTP, PIN plus TOTP and password plus PIN plus TOTP. Passwords and PINs use individually salted PBKDF2 SHA-256 verifiers with 310,000 iterations. TOTP uses RFC 6238 with SHA-1, SHA-256 or SHA-512, six through eight digits and configurable periods. Registration confirms a current code. Credentials are excluded from list metadata. Lock sessions exist only in memory and expire or end when the application closes. Wrong attempts trigger capped exponential waiting after five attempts.

`guard()` must wrap every protected callback, including keyboard shortcuts and command-palette routes. Capture-phase interception additionally stops pointer, keyboard, input, change, submit and drag events. This is a convenience feature and cannot protect against a user who controls the renderer or deletes local data. It does not encrypt user files.

AES-GCM cache helpers use a non-extractable session key, fresh IVs and a stable record identifier as authenticated additional data. A session key is deliberately not persisted. Persistent encryption requires a host-managed vault key, not an exported renderer key.

The local profile setup stores a salted verifier in the supplied vault. Explicit unlock derives a separate non-extractable AES-GCM key from the password and profile salt, then calls `onAuthenticatedChange(true)`. Logout and destruction discard the key and call `onAuthenticatedChange(false)`. `encryptPrivateCache(value, identity)` and `decryptPrivateCache(record, identity)` reject access while logged out. The host may persist only the returned ciphertext, and must clear any previously rendered private wording immediately on logout. The profile is local and does not create a network account or session. Five failed profile attempts trigger capped exponential waiting in the current renderer session; persistent attempt budgets require a host service.

## Current limitations

The host must assign stable identifiers and bind every protected element; automatic per-element context-menu discovery and anchored wizard placement are not complete. `openLockWizard(id, originElement)` populates the correct target, focuses the policy, and restores origin focus on cancellation. The wizard displays only the selected policy's factors and includes a PIN keypad. Removing a lock authenticates first. Timed and until-close sessions are implemented; one-activation duration is not implemented.

The local waiting ladder is reachable from an element unlock prompt during a waiting period. It exercises nonce consumption, expiry, three skips per rolling hour, arithmetic progression and timed unique mole scoring. Its controller operation changes only the waiting deadline, retaining failed-attempt count and escalation and never creating a credential session. Under School mode it starts at arithmetic without mentioning dishes. Outside School mode, a missing reviewed catalog starts arithmetic with an explicit availability explanation. Optional `getDishChallenge()` must synchronously supply four factual choices, a prompt, answer index, and `catalogSource` equal to `https://github.com/Ding-Ding-Projects/dim-sum-photos`; the host owns catalog acquisition and verification. No sample dish puzzle ships as a default. It must not be treated as an authoritative anti-abuse mechanism: challenges and grading are renderer-local and a privileged challenge service is not implemented. The profile unlock now exposes the same ladder during its own waiting period. Do not expose it as production authentication protection.

`access/copy.js` contains English-to-Cantonese strings for fixed controls, local errors and ladder content. The surface delegates translation and message styling to `services.translate(text, options)` or `services.t(key, fallback, options)`. User-supplied account, issuer, ticket text, numeric codes and stable identifiers remain factual. The unstyled local-only privacy disclosure is translated without message styling.

Authenticator URI/manual parameters, issuer/account/group editing, order persistence, substring/regular-expression search, deletion, live codes, next-code preview and vault index restoration are implemented. Edits require current-code confirmation and do not reveal the stored secret. Local SVG QR generation preserves a four-module quiet zone and black-on-white contrast. Registration details appear only after explicit reveal and are removed on successful registration, hide, or logout. Image-file and clipboard decoding accept PNG, JPEG, WebP and GIF inputs up to 8 MiB and 4 megapixels. Camera scanning requests video only, runs for at most 60 seconds, and stops tracks on completion, cancellation, logout and destruction. Camera or clipboard permission refusal is reported without a network fallback. Bundled encoder and decoder provenance is documented in `src/renderer/features/access/vendor/README.md`.

Bulk management, clock-skew diagnostics, encrypted mutation-history host integration and authenticated export remain integration work. Mutation metadata callbacks are awaited and contain only action and stable identifier. No external QR service is used. The support list uses bounded local storage for at most 100 records, with 100-character categories and 2,000-character descriptions. It is searchable, editable, advances through local statuses and permits individual removal; it has no export or bulk management yet, and its fixed privacy disclosure follows the current language. Built accessibility/layout verification remains pending.

## Verification

`node --test test/local-access.test.js` verifies every published RFC 6238 vector for all three algorithms and six/eight digits, salted verifiers, authenticated-cache identity mismatch, large-cache conversion and bounds, all six policies, independent sessions, expiry, ladder nonce/budget behavior, and a complete local QR encode/decode round trip preserving registration parameters. These tests verify the component logic, not complete host integration, physical-camera behavior or a built visual surface.

## Protected record format 2

Password verifiers and encryption keys use distinct, versioned purpose prefixes in their PBKDF2 salt inputs. A persisted verifier is never reused as an AES key. Format-2 encrypted records also bind their version and record identity as AES-GCM associated data.

Legacy format-1 password verifiers remain usable for password verification, but format-1 encrypted records are explicitly rejected. Those records used a derivation whose encryption key equalled the persisted verifier. They cannot be made retrospectively confidential. The application does not silently decrypt, upgrade, or describe them as protected: retain a copy if needed, reset the affected local record and re-import from a trusted original through an explicit user action. New ciphertext created after a legacy password check uses the separated format-2 derivation.

Creating a lock for an existing target is rejected, including a target found only in the persistent store and concurrent creation attempts. The existing lock must be authenticated and removed before a replacement is created. Logout and destruction invalidate pending profile unlock operations; late password derivations cannot restore an authenticated session.

## Cancellation and live refresh

Every element uses a generation counter for asynchronous authentication. Relock, prompt cancellation and removal invalidate prior attempts. Authentication checks the current generation before installing a session. Removal requires an unlocked current generation and rechecks it around asynchronous storage access; a cancellation during deletion restores the original persistent record before returning an incomplete result.

The access mount exposes `refresh()` for host language and mode updates. It updates registered static text and rebuilds live lists while preserving profile authentication and user-entered field values. An open waiting challenge closes during refresh so a newly enabled School mode cannot leave a prior dish challenge visible. Supply `translate(source, options)` and either a boolean or live function for `schoolMode`.

## Persistent hourly waiting budget

Element and profile challenges share a non-secret, versioned local record containing at most three skip timestamps and random operation identifiers. The default key is `material-file-encryptor.wait-budget.v1`. Restarting or creating another budget manager does not replenish the three-use rolling-hour allowance. A successful challenge reserves a use before it may clear a waiting deadline; it never grants a session, changes credentials, reduces escalation or adds password attempts. Cancellation during reservation may conservatively consume a use, but cannot unlock or clear the wait.

The default browser implementation serializes reservations through Web Locks. A desktop host may supply `withLocalLock(name, callback)` backed by its shared local-data serialization mechanism, or supply a complete `waitBudget` adapter. Missing serialization, corrupt records or storage errors fail closed to waiting for the timer. No password, PIN, TOTP secret or user document enters this record. This preserves a local convenience budget, not a tamper-resistant security boundary: clearing application storage remains the documented reset route.

`test/local-wait-budget.test.js` checks concurrent consumers, manager recreation, the inclusive hour boundary, invalid storage, unavailable serialization, profile waiting-only success, cancellation during reservation and actual profile-ladder UI reachability. Failed-password attempt counters and waiting deadlines remain session-local; only the skip allowance is persisted by this module. The authoritative service-side challenge boundary and broader native shared-state integration remain explicitly unimplemented.
## Activation sessions and selected-record management

The lock wizard offers timed/until-close sessions and one-activation sessions. `guard(id, callback)` consumes a one-activation grant before invoking the callback, including callbacks that throw or attempt reentry. DOM interception consumes it on an allowed click, change, submit or drag start, not pointer preparation. A compound workflow emitting more than one intercepted action must authenticate for each action or use a single host-owned guarded callback. Existing saved locks default to timed sessions.

Authenticator rows support selection, select-visible, clearing selection and confirmed bulk removal. Cancelling during asynchronous deletion restores the removed records; concurrent removal is serialized within the mounted surface. Selected metadata export requires an unlocked local profile and explicitly excludes secrets and generated codes. It is an account inventory, not a recoverable authenticator backup. Clock alignment diagnostics compare a supplied current code locally within four periods either side; they report an offset, ambiguity or no match and never change the host clock. Diagnostics do not replace authentication.

Local tickets support selected export and confirmed bulk removal. Export includes the selected descriptions and the existing local-only disclosure. Users must review descriptions for private information before manually sharing the exported file; the application sends nothing automatically. Ticket content remains ordinary local storage, not encrypted credential storage.

Focused coverage includes activation consumption/reentry, authenticated allowlisted exports, bounded clock matching, selected ticket exports, UI reachability and cancellation during an asynchronous bulk deletion. Full browser and native integration evidence is separate.

For combined capture and host handlers, use `guardEvent(id, event, callback)` with the exact current DOM event. A single-use, generation-bound admission carries the already-consumed activation to that handler and expires at the next microtask. Explicit relocking invalidates it immediately. For a palette action that generates events, use `guardControl(id, control, callback)`: it admits one synchronous synthetic button click, or one input/change pair on that exact control, while the callback runs. Nested guarded calls and later events remain locked. Plain `guard` is for callbacks that do not dispatch intercepted events.
