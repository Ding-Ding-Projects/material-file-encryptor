# Runtime rejection evidence

## Exact history restore identity

History restore verification identifies the version selected by the fixture, then finds that exact ID on the rendered restore control. The ID is metadata from the existing handler's version identity; it does not change restoration semantics. A separately fetched backend row position cannot identify a row in the renderer's independently loaded and filtered snapshot.

Before selection, the verifier requires a ready archive, `aria-busy="false"`, matching request/completion markers and matching render/rendered generations. It records the bounded requested identity, matching count, visible/enabled state and generation markers, then requires exactly one visible enabled control. The click uses the same exact ID. Missing, duplicate, hidden, disabled or stale targets fail explicitly; no position fallback is permitted.

If an action fails, a later diagnostic query or write cannot replace its exception. The original object and code are rethrown, with separate observation/save faults when available. An unsuccessful query never becomes a fabricated observation. Restored file bytes and retained-history assertions remain required after a real successful action.

Twenty focused checks cover reordered backend inventories, stale generations, identity encoding, absent/duplicate/hidden/disabled controls, bounded observations and combined action/query/write failures. These checks and independent source review establish the verifier correction, not a fresh built runtime or installation verdict. The earlier source55 restore attempt stopped before invoking restore and remains failed evidence.

When the installed lifecycle validator exposes a bounded rejected ancestry edge, the project adapter records it before the canonical command handler sanitizes the exception. It rethrows the original exception without authorizing any additional process action.

The recorder accepts only the versioned producer fields for missing-parent or child-before-parent rejection. It validates the exact child and optional parent identity, claimed parent PID, 100 ns creation ticks, absence/order statement and 64 KiB edge bound. Unsupported or unavailable metadata remains unrecorded.

Private records use exclusive new `rejected-edge-<random-id>.json` files directly below the validated saved lifecycle run root. The lifecycle file must be that root's `lifecycle.json`, its saved process must match the rejected validation root, and its state must remain created and not cleaned. Link/reparse components, changed lifecycle state, wrong output roots, existing destinations and unverifiable readback are rejected. On Windows the directory chain is pinned without delete sharing during creation. Each retained record contains the source lifecycle SHA-256, root identity and exact rejected edge. These records remain private diagnostic evidence and must never be published or packaged.

Standard output carries only sanitized failure codes, allowlisted reason/stage and neutral saved/unavailable counts. It never includes the private edge, executable paths or raw native messages. Recording failure preserves the original lifecycle rejection and leaves processes untouched. This evidence explains why proof stopped; it cannot establish process ownership or permit termination.

Focused offline tests cover exact missing-parent and timestamp-order records, unchanged exception identity, multiple retained records, strict schema and size rejection, stale lifecycle context, ownership mismatch, exclusive creation, reparse rejection and stdout redaction. No live desktop verdict is implied by these tests.

## Bounded ownership proof for each fresh CDP attachment

Every runtime, control, capture and modern-observation plan uses the shared `withCdpConnectionProof` helper to request `startupOwnershipAttempts: 3`. The identifier describes startup of that CDP connection, not only application startup: each plan opens a fresh attachment. Recovery, final restoration and normal teardown explicitly remove any inherited opt-in and retain the installed driver's one-attempt default.

The installed driver accepts only integers from one through three. A retry is permitted only for `INVALID_NODE_IDENTITY` when the exact launch root remains valid and the rejected attempt's private snapshot was saved successfully. Each attempt acquires a fresh complete pre-attachment ownership proof, with 500 ms between attempts. Definitive impossible ancestry takes precedence over incomplete rows and remains terminal. Every rejected proof is retained; missing private evidence, root change, any other rejection, or exhausted attempts stops attachment. An earlier failed proof never supplies ownership for a later attempt.

The shared helper only annotates plans. It does not execute or retry any action sequence, partially completed plan, target-isolation check, recovery or teardown. Strict single-target and identity checks remain unchanged. Source-bound receipts retain every executed plan's actual result and rejection evidence. Focused checks prove purpose routing, inherited-budget removal, and single execution when a plan fails after partial work; they do not claim a successful live replay.

## Native proof for the newly created empty drive

Before converting the synthetic GUI-created vault to the legacy fixture format, verification proves the mounted root is empty through `native-empty-root-proof.py`. This replaces the assumption that Node `fs.readdir` can enumerate an empty WinFsp root. A real packaged 1.33.1 reproduction opened a valid directory on the expected MaterialVault volume, then observed the first `NtQueryDirectoryFile` completion as `STATUS_NO_SUCH_FILE` with zero bytes. Node 26.10.0 with libuv 1.52.1 reported `ENOENT` for that same mounted root. This is an enumeration compatibility result, not evidence that the mount was absent.

WinFsp's pinned [directory completion implementation](https://github.com/winfsp/winfsp/blob/ddca7bd5481857a65ba552f643b8776fd070836f/src/sys/dirctl.c) returns `STATUS_NO_SUCH_FILE` for an initially empty result and `STATUS_NO_MORE_FILES` at the end of enumeration. The verifier accepts only those two statuses with zero returned directory data. It does not catch and reinterpret arbitrary `ENOENT`, add directory entries, or change the product, vault format or public API.

The caller requires a freshly prepared owned GUI fixture, its saved drive reservation, exact storage/cache paths, and mounted, unlocked, idle status before and after the native query. The native helper opens the root with directory-list and attribute-read access, retains the handle throughout the query, and compares directory attributes, exact file ID and volume identity before and after. A separately reopened root must match the retained handle. Both handle and volume serials must agree and the filesystem must be `MaterialVault`. Missing roots, files, nonempty data, other statuses, changed identity, unsupported platforms and timeouts fail closed. The asynchronous query waits at most five seconds, then cancels and waits at most five more; buffers remain alive through cancellation or process exit. The caller imposes a twelve-second process bound.

A successful proof writes an exclusive private `gui-empty-root-proof.json` below the validated lifecycle run root. It records the packaged source and executable hash, native and fixture helper hashes, lifecycle hash, exact native status, before/after/reopened identities and explicit empty verdict. Existing records are never overwritten. The receipt and fixture paths remain private. This proof is required before locking and legacy conversion; it cannot authorize an unrelated drive or process action.

File IDs and volume serials are canonical decimal strings, with unsigned 64-bit and 32-bit bounds respectively. The native producer compares them before serialization, and the JavaScript consumer validates their exact string representation without number conversion. The earlier reproduction's numeric file-ID field is retained as historical evidence and cannot support exact JavaScript roundtrip identity claims.

Focused tests exercise both permitted statuses, nonempty data, unexpected status, changed root and volume identity, wrong filesystem, absent root, ordinary file, changed mounted/lifecycle binding, unsupported platform, timeout and existing-receipt rejection. A real fresh ordinary NTFS directory comparison is read-only and is explicitly rejected as MaterialVault evidence. Fake callbacks test decision boundaries only; they do not establish native or desktop behavior. The original packaged reproduction remains separate evidence, and the new helper still requires integration replay before full runtime acceptance.

## Legacy fixture history and failed-run retirement

GUI creation establishes host-owned ciphertext history for the selected storage identity. Rewriting that pair's configuration from format 2 to format 1 conflicts with the previously recorded immutable `vault.json` object, even when the vault contains no user files. A fresh hidden replay reproduced the synchronization rejection after successful format-1 mounting and mounted write/read; the retained history header and current header had different object hashes. The fixture was wrong. Product immutability remains unchanged.

After native emptiness and locked-state proof, the verifier now creates exclusive `legacy-storage` and `legacy-cache` directories in its owned synthetic root. It copies only the empty vault configuration, changes the copied headers before their first host registration, and opens that fresh identity through the real controls. The GUI-created format-2 pair and its history are preserved. Existing destination directories are rejected. Copy upgrade continues to use another fresh pair and independently reopens the legacy original.

Action polling now stops when the interface reports an error, retains its bounded message in the private step receipt, and rejects the action immediately. It does not turn backend rejection into an opaque timeout or treat it as successful synchronization.

Before GUI, legacy or upgrade actions can create credentials, an exclusive owned-fixture record binds their exact storage/cache pair to the original fixture and helper. After verified process absence and desktop closure, retirement validates those records and forgets every registered pair, then removes only the exact generated key. Failure before runtime completion takes the same retirement path. Records and synthetic ciphertext/history remain retained; retirement reports which pairs were processed and does not claim the runtime passed.
