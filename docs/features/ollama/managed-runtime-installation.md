# Managed Ollama CLI installation

Model Store provides a dedicated installation workflow for a missing managed local runtime. The desktop host requires native confirmation before downloading the pinned complete official Windows CLI ZIP. It installs into an application-owned immutable version directory. Existing Ollama installations, model folders, system PATH, startup entries and services are retained. Installation does not start Ollama or establish API health.

The admitted candidate is Ollama v0.40.3 for x64: the official `ollama-windows-amd64.zip` contains 1,468,053,171 compressed bytes, with SHA256 `e5ecff02dfc7cae8ddf6d6b7a7ac5f727ffeedf4491f44ae75ff5b0820dbbbd5`. Its independently decoded source manifest records 82 files and 1,941,752,691 expanded bytes. ARM64 remains unavailable until a complete equivalent file manifest is reviewed. Optional ROCm and MLX packages are not installed by this workflow.

The host streams bounded downloads, verifies exact size and digest, and reuses only matching cache bytes. Redirects are restricted to the official release delivery hosts. Rejected caches and incomplete downloads are retained for diagnosis. The fixed Windows PowerShell helper uses .NET ZipArchive directly, hashes the same protected archive stream it extracts, holds ancestor directory identities, rejects unexpected members and special file types, and checks every extracted file against the reviewed SHA256/size manifest. The helper receives only bounded nonsecret operation configuration in its private child environment, clears that field before extraction, and emits fixed phase or failure categories. No archive content is executed.

A valid exact publisher and certificate policy remains required for `ollama.exe`. A protected credential record anchors the admitted complete tree, rather than trusting a mutable receipt alone. The host publishes the version directory atomically, persists that protected admission, and checks the tree again. Unknown or modified existing destinations are not overwritten. Every managed launch revalidates the entire file tree and publisher, uses its owned working directory and a restricted executable search path, and remains a separate explicitly confirmed action.

Installation events contain only an operation ID, fixed phase/outcome/reason, bounded byte counters, version, architecture, cancellation availability and installed state. They contain no host paths, commands, credentials or archive payloads. Browser callers cannot install or cancel a native installation. Read-only status remains bounded.

Cancellation targets the exact active operation. During extraction it creates a fresh owned cancellation marker only after the helper confirms its directory protections. The helper observes cancellation between bounded stream chunks. The host waits for confirmed helper exit before removing a marker whose original identity and fixed content still match. Replaced or uncertain markers remain retained. Atomic publication and protected registration settle without cancellation. Closing the service waits for owned installation work, and installed-stopped remains distinct from a running or healthy service.

Focused synthetic checks cover protocol admission, cache and download refusal, full-tree changes, publisher rejection, directory and archive leases, extraction hashes, Unix file attributes, cancellation and close ordering. The actual official archive download and nonexecuting manifest decoding are verified. Source review, packaging, a genuine button-driven installation, owned runtime launch, API health, model execution and rendered accessibility/layout acceptance remain separate pending checks. No end-to-end installation or runtime claim follows from these source checks.

The managed runtime controller exposes Stop only for its retained native owner. API health, a port or a process ID never establishes ownership of an external runtime. Stop reserves the service lifecycle before asynchronous work, refuses overlapping model preflight or operations, and requires exact job exit plus runtime lease release before reporting success. Unknown settlement retains the owner for retry. Browser callers cannot stop the native owner. Installation and startup confirmations support English, Cantonese and bilingual modes through bounded per-request language selection.

The published native synthetic verifier has exercised the shared production lifetime algorithm: an exited original parent retained its exact handle while a recorded live descendant remained inside the job and runtime files stayed protected. Stop and EOF settlement required the complete job to reach zero before releasing leases. Additional contained console infrastructure is part of that job, so a fixed process-count assumption is not used as descendant proof. This is synthetic lifetime evidence, not official Ollama execution or button acceptance. A fixed native startup admission is now enabled in source after that proof, while production installation, API health, actual button interaction and rendered accessibility remain pending. Directory insertion prevention and abrupt host-death ordering remain unverified limitations.
