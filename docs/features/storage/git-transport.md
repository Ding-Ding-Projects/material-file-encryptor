# Encrypted Git history and private repository transport

`GitVaultHistory` uses the bundled or installed `git` CLI to create actual commits, trees and binary blob objects. Its working directory and mutable `.git` directory must be local and outside the vault source folder. Only `vault.json`, `parts/<opaque-id>.mfe` and `commits/<opaque-id>.mfe` are accepted. Identifiers are hexadecimal with 32 or 64 characters. No original filenames, file paths, credentials or unencrypted snapshot metadata are written into commit messages or tree names. Commits use a generic storage identity and message. Ciphertext files and the cryptographic vault header are immutable: conflicting bytes fail the operation.

Call `RecordSnapshotAsync(paths)` after encrypted children and their snapshot metadata have been published. Supply explicit source-relative files rather than enumerating all historical payloads. Every supplied file must already exist locally. On a partial client, include available new chunks and metadata, not missing historical chunks. Recording no changes creates no empty commit. `ListSnapshotsAsync` lists commit identifiers without reading payload objects. `ReadEncryptedFileAsync(commit, path)` retrieves an encrypted historical file and can hydrate that one promised blob.

`FolderVaultTransport` retains the ordinary folder provider. It validates requested paths and checks availability; the existing engine remains responsible for immutable child-first publication. It never copies mutable Git state into the synchronized source folder.

`PrivateGitHubVaultTransport` is selected per vault using a strict `owner/repository` identifier. It requires an existing private GitHub repository and GitHub CLI authentication. Repository privacy is checked through `gh repo view` before cloning and again before synchronization and publication. The configured origin must match the selected repository. Git ignores system and global configuration, resets credential helpers to the trusted GitHub CLI `auth git-credential` mechanism, and disables interactive prompts. Effective fetch and push destinations must each resolve to exactly the selected private repository; push URLs and local URL rewrites cannot redirect publication. Tool output is not included in transport exceptions, avoiding accidental credential or local-path disclosure.

The private provider needs a dedicated empty local history directory, separate from any ordinary local history directory. It clones with `--filter=blob:none --no-checkout`, never performs a working-tree checkout and materializes encrypted commit metadata and the root vault header explicitly, and requires promisor configuration with the `blob:none` filter. An existing full clone is rejected rather than described as lazy. A server reporting unsupported filtering is rejected explicitly. Fetching and listing trees do not request historical part blobs. `EnsureFileAsync("parts/<id>.mfe")` retrieves one selected encrypted object using `git show`, then publishes it atomically into the vault source folder. Metadata synchronization materializes encrypted commit files only.

Synchronization fetches the current main branch, validates its tree paths, and builds a validated immutable tree union and a real Git merge commit. Concurrent immutable snapshot additions produce a real merge commit with both parents. It never force pushes. A conflicting immutable object or vault header stops reconciliation. A writer winning the race between fetch and push causes a normal rejected push; retry synchronization after checking the vault state. Git authentication, network, merge and publication failures remain explicit failures, not successful offline synchronization. Empty repositories remain empty until a real snapshot is recorded.

The engine integration attaches its encrypted-file hydration delegate to `EnsureFileAsync`, records available newly published snapshot files after `HistoryChanged`, and invokes transport synchronization before replaying newly received encrypted metadata. The controller owns backend selection and local paths; neither backend requires a plaintext filename or encryption key. Do not place the history directory inside a synchronized folder or reuse it across vaults.

## Verification

Run `dotnet run --project native/MaterialFileEncryptor.Transport.Tests`. The standalone executable exercises actual temporary Git repositories and a local filter-capable Git server, including binary blob round trips, older snapshot reads, unchanged snapshots, invalid paths, immutable collisions, overlapping storage rejection, privacy rejection before Git access, generic commit messages, missing promised blobs after metadata synchronization, on-demand hydration, concurrent snapshot reconciliation and two-parent merges. GitHub CLI privacy responses are injected for these tests. Live GitHub authentication and network service availability require separate operational verification.

## Process and conversion isolation

`VaultProcessRunner` accepts explicit trusted executable paths, otherwise prefers `resources/tools/git/cmd/git.exe` and `resources/tools/gh/bin/gh.exe` beneath its application base directory, then falls back to PATH. Missing tools produce a clear availability error. Each process has a linked 60-second timeout and cancellation kills its process tree. No tool downloads occur in this component.

Recording rejects unrelated staged paths without discarding them. The complete resulting tree is validated and contains regular ciphertext files only. `hash-object --no-filters`, `update-index --cacheinfo`, `write-tree` and `commit-tree` avoid clean/smudge filters, attributes and custom merge drivers. Synchronization also uses tree plumbing instead of checkout or worktree merges, so ciphertext remains byte-exact even with hostile local attributes. Serialize record, sync and hydration calls in the owning controller.

`ContainsFile(path)` answers from the last validated tree-name inventory and never requests a blob. An empty private destination synchronizes without inventing a commit or publishing another branch. Tests also cover staged plaintext preservation, hostile clean filters, exact bytes despite attributes, redirected push URLs, effective push rewrites, and empty destinations.
