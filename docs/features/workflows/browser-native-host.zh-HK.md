# 瀏覽器原生訊息傳輸

`MaterialFileEncryptor.BrowserHost.exe` 為
`org.dingding.material_file_encryptor.downloads` 提供 Windows 原生訊息傳輸。
主機有兩種模式：由瀏覽器啟動時，先核對設定內允許嘅來源，再透過同用戶命名管道
轉送訊息；桌面程式以隱藏、自行管理嘅子程序啟動 `--broker`，經標準輸入輸出
交換有關聯編號同長度限制嘅訊息。傳輸層唔會開啟保管庫、處理檔案明文，
亦唔會將瀏覽器配對憑證儲存到磁碟。

正式管道名稱由目前 Windows 用戶嘅 SID 衍生。用戶端同伺服器都要求
`PipeOptions.CurrentUserOnly`。伺服器會讀返真實 DACL，只有當佢包含單一允許項目，
指定目前用戶嘅實際 SID，而且有讀寫權限，先會接受。權限缺失、範圍過大或者
不符合預期，代理程序會喺報告就緒之前停止。呢個檢查避免將部分 .NET 版本採用嘅
權杖擁有者 SID 當成實際用戶 SID。完整性或者提升權限層級不同，仍然可能令連線
失敗。支援路徑要求桌面程式同瀏覽器使用相同嘅一般用戶權限層級。

## 同意同下載狀態

擴充功能來源字串係允許清單資料，唔係瀏覽器身分證明。同一用戶執行嘅程序可以
手動啟動主機，亦可以連接該用戶嘅管道。因此每次新配對都要喺已解鎖嘅桌面程式
明確批准。同意畫面要指出所申請嘅來源，並解釋傳輸層無法驗證手動啟動嘅同用戶
程序。預設選項係拒絕。批准配對唔等於批准下載，亦唔等於批准目的地。

JavaScript 代理將配對同下載建議交畀 `createBrowserDownloadReceiver`。
工作階段只保留喺記憶體，15 分鐘後到期，每個工作階段最多接受 64 個不重複建議。
已接受建議只會轉送到主機專用 `receiveBrowserProposal` 方法，畫面程序無法呼叫。
原生目的地選擇器同明確「開始下載」動作仍然係獨立步驟。

擴充功能可以用精確嘅 `{type:"status",session,id}` 訊息查詢自己嘅建議。
代理根據真實桌面下載事件報告 `awaiting-confirmation`、`downloading`、`completed`、
`failed` 或 `cancelled`，以及位元組進度。關聯編號會以 `browserCaptureId`
保留喺佇列項目。狀態回覆唔包含目的地路徑、網址、明文或者憑證。
桌面鎖定時必須撤銷代理配對，離開時必須關閉自行管理嘅子程序。

`close()` 會即時撤銷接收權限，同時呼叫嘅用戶會共用同一份非同步收據。
喺三秒限時內，佢會觀察自行管理嘅程序離開、全部繼承標準輸入輸出串流關閉，
以及未完成回覆 callback 嘅狀態。收據包含 `processExited`、`stdioClosed`、
待處理要求／回覆數目同 `verified`。未觀察到程序離開、串流未清空，或者原生
同意仍未完成，`verified` 都會保持 false。唔會終止無關程序，亦唔會將發出終止
要求當成程序已離開嘅證明。
如果之前收據未核實，之後重試會重新觀察目前程序離開同清空狀態。
已成功完成嘅收據會保持不變。

桌面程式由綑綁 `browser-host` 目錄初始化 `createBrowserHandoffLifecycle`。
已審閱設定缺失或者無效時，代理程序唔會被建立。桌面隔離驗證模式亦會停用正式
代理，令合成測試同目前用戶流程分開。啟動接駁原生同意、解鎖／關閉接收限制、
主機專用建議傳送同下載事件。每次發佈已鎖定或者助手未核實狀態，都會撤銷配對。
離開、更新準備同驗證退出會先等到已核實關閉收據，先完成服務關閉。
`getState` 包含真實 `browserDownloadHandoff` 狀態同最後關閉收據。

啟動失敗處理器會喺 `app.exit(1)` 前使用相同已核實關閉界線。
收據未核實時，桌面程式保持運行、記錄需要恢復狀態，並提供原生「保持運行／
重試關閉」選項，預設保持運行。重試會重新核對同一自行管理程序同串流證據。
恢復對話框不可用時，程序亦會保留並報告未核實狀態。
啟動失敗唔代表可以遺下未核實代理程序。

一般桌面功能 IPC 有獨立存取 context 界線：主程序核實要求 frame 後，會將真實
`event.senderFrame` 作為第四個原生服務參數傳送。主程序管理嘅 frame getter
回傳 `window.webContents.mainFrame`。畫面 payload 唔可以提供 actor，loopback
adapter 呼叫會保持缺少 context，唔會借用目前畫面 frame。
存取 adapter 必須拒絕缺少 context 嘅要求。原生下載建議繼續用主機專用路徑，
唔會捏造畫面存取身分。

## 身分同登記計劃

`scripts/browser-native-registration.mjs` 接受已審閱嘅 CRX3 套件，以及第 1 版
公開身分收據。收據包含 `format`、`signatureVerified`、`extensionId`、
`publicKeyDerBase64`、`packageSha256` 同 `publicKeySha256`。
程式會獨立核對套件同公開金鑰雜湊、由公開金鑰衍生擴充功能 ID、檢查 CRX3
已簽署身分，並核實涵蓋已簽署標頭同內容嘅對應 RSA 或 ECDSA 簽章。
單靠收據寫住成功唔會通過驗證。未簽署嘅原始碼套件唔會被接受。

產生器亦要求已正規化嘅絕對安裝主機路徑同資訊清單路徑。佢會輸出原生主機
資訊清單、`browser-host-config.json`，以及 Chrome 同 Edge 嘅精確 HKCU 登記計劃。
佢唔會執行登記指令、安裝或者移除主機、改動瀏覽器設定檔，亦唔會開啟用戶瀏覽器。
已有輸出檔案會保留，唔會被覆蓋。未有已審閱套件身分時，原生交接保持不可用。
唔會將佔位擴充功能 ID 當成可信身分出貨。

建置將執行檔編譯到 `out/browser-host`，封裝要包含該目錄，以及存在時已核實嘅設定。
主機沿用現有未簽署 Squirrel.Windows 封裝路徑。編譯或者綑綁傳輸層唔會證明
已安裝呼叫者可信、主機登記成功、擴充功能已發佈、已安裝更新成功，或者移除成功。
實際安裝同已安裝更新／移除流程仍然延後。

`build.bat /s /browser-host-only` 係此傳輸層嘅聚焦正式建置入口。
佢會執行現有相依項目啟動同詞彙檢查、發佈真正獨立 Windows 執行檔，並將原始碼
同執行檔雜湊記錄到 `out/evidence/browser-host-build.json`。
佢唔會封裝或者安裝桌面程式。完整 `build.bat /s` 路徑會喺封裝前發佈同一主機。

## 限制同驗證

全部傳輸訊息使用四位元組小端序長度、嚴格 UTF-8 JSON，以及 64 KiB 上限。
空白、過大、截斷、重複欄位同不安全原型欄位輸入都會被拒絕。
代理最多接受兩個連線用戶端，每個連線最多 256 個要求。
子程序啟動限時五秒，已連接要求限時 35 秒。傳輸診斷唔會包含訊息內容或者
工作階段值。

`test/browser-native-host.test.js` 驗證即時簽署嘅合成 CRX3 測試資料、簽章竄改、
收據不符、路徑拒絕、明確同意、未知欄位、重播同工作階段到期、來源允許清單、
三個流程狀態、有關聯編號嘅子程序訊息，以及過大輸入拒絕。
原生執行檔嘅 `--self-test` 路徑驗證訊息拒絕同獨立自行管理嘅同用戶管道，
包括真實 ACL 讀回同訊息往返。呢啲測試唔會接觸真實保管庫、已掛載磁碟機、
瀏覽器設定檔、登錄項目或者安裝。已安裝瀏覽器行為同三個可見桌面畫面，
要有另外嘅真實已安裝證據，先可以聲稱已驗證。

此聚焦傳輸實作已通過精確正式建置入口同 10 個原生合成檢查。
向 JavaScript 測試提供該建置嘅 `MFE_BROWSER_HOST_EXE` 時，14 個測試全部通過，
冇略過。編譯主機測試將主機複製到全新自行管理嘅測試目錄，只加入產生嘅合成設定，
以隱藏模式啟動兩個真實轉送程序，核實明確配對、建議、等候／下載中／完成狀態
同重播拒絕，然後關閉自行管理嘅程序並移除測試目錄。
呢啲係傳輸同通訊協定結果，唔係已安裝瀏覽器或者可見桌面驗收證據。
