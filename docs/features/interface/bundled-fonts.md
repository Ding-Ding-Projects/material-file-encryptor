# Complete local bundled fonts

The source inventory pins complete official Noto Sans normal and italic variable
fonts (version 2.008), and the full Noto Sans CJK HK variable font (version 2.004).
The Hong Kong font is not the regional subset file. These are deliberately pinned
versions, not a claim that they are the newest releases.

`src/shared/fonts/manifest.js` records immutable upstream revisions, trusted
download URLs, exact byte sizes, SHA-256 hashes, parsed axes and named instances.
Both official SIL Open Font License 1.1 notices are downloaded, hash-verified and
distributed beside the unchanged fonts. Source provenance is the official
[Noto fonts distribution](https://github.com/notofonts/noto-fonts/tree/ffebf8c1ee449e544955a7e813c54f9b73848eac)
and [Noto CJK Sans 2.004 distribution](https://github.com/notofonts/noto-cjk/tree/523d033d6cb47f4a80c58a35753646f5c3608a78).

## Staging and integration

Run `node scripts/stage-bundled-fonts.mjs`, or call `stageBundledFonts` with explicit
output/cache directories, cancellation signal and progress callback. Downloads
follow the project's pinned-source cache pattern. They are streamed with a size
bound, timeout and exact hash verification. A complete temporary tree is verified
before atomic publication. Failed or cancelled staging does not publish that tree.
An existing matching tree is verified and reused; conflicting content is rejected.
Linked staging paths are unsupported.

The returned `rendererDirectory` and `siteDirectory` each contain local
`fonts.css`, three complete font files and two license notices. Copy the complete
directory into each product's packaged/local asset tree and load its CSS. CSS has
only relative asset URLs, no external runtime font requests and no glyph subsetting.
`bundledFontDescriptors` requires a same-origin directory URL and reports
unavailable until the integrator supplies verified asset presence. Staging means
`staged-awaiting-renderer-validation`, not proof of rendering.

Unique CSS aliases distinguish normal, italic and Hong Kong resources. Original
font family/style metadata is retained separately. The appearance integration
must explicitly map those aliases and styles before applying variable axes.
The existing picker intentionally rejects unmapped italic or Thin style metadata;
it must not silently relabel those faces as Regular merely to admit a selection.

## Evidence and remaining work

The authoring cache contains the actual verified official files. Both local
staging trees were produced from that cache with download disabled, then all
font/license bytes and CSS were verified. Focused tests reject incomplete or
wrong hashes, cancellation and unrelated network origins. Generated bytes remain
ignored under `font-assets/` and `.cache/`; they are not committed to ordinary
version control or standard Git LFS. No supported cloud-transfer publication was
established in this unit, and none is claimed.

Build and website source hooks now copy and verify the complete local tree,
including both licenses, and generate a receipt module containing the manifest
identity and exact asset sizes/hashes. Packaging includes the renderer font tree
and excludes the staging cache. The existing root entrypoints remain unchanged.

The source loader imports only the same-origin receipt, verifies the complete
manifest identity, then loads local FontFace aliases. It admits the three known
alias/style mappings only after their load promises complete. Original metadata
still identifies the italic and Thin faces honestly. Installed faces retain their
conservative restrictions. Loaded aliases belong to the document, so closing an
editor cannot remove a saved appearance font. The constructor, load and document
registration behavior follows the [CSS Font Loading specification](https://www.w3.org/TR/css-font-loading/).

A cache-only integration check copied five assets totaling 41,738,686 bytes to
both ignored renderer and website trees with zero download calls. Component
checks exercise the actual loader code with injected FontFace consumers, not a
real browser. Wrong receipts, missing staging, partial decoding and cancellation
cannot admit the inventory. Actual root production, native bridge admission,
inspected rendered glyph identity, complete typography and replacement screenshots
remain unverified. No system font was installed and no product GUI or heavy build
was run.

## Initial declarative registration

The website home and desktop initial HTML entries link the local ./fonts/fonts.css stylesheet before their module scripts. Existing staging copies this exact stylesheet and its three font assets into each fonts directory; stylesheet asset URLs resolve relative to that directory. No runtime CDN or additional dependency is introduced. The asynchronous catalog, manifest/receipt validation and original font-selection authority remain unchanged. Declarative registration can populate FontFaceSet before an editor opens, but does not prove successful decoding, glyph coverage or rendered face identity. Those observations require a fresh built capture.

Generated documentation shells also declare the same local font stylesheet. Root library/wiki/gallery routes use ./fonts/fonts.css; article/category/wiki-article routes use their relative parent prefix. The publication helper derives the prefix from bounded route depth, including deeper nested routes. Tests parse actual helper-produced stylesheet links and resolve them against route URLs, rejecting missing and external font links. Asset staging and the registration-versus-decoding boundary remain unchanged.

The separate browser workspace also links ./fonts/fonts.css before workspace.css and its module script. It resolves the same staged local assets under the unchanged self-only style/font authority. Source review does not establish updated live inventory, font decoding or rendered workspace typography.
