# Scheduled settings schema and temporary customization

Rules persist in local settings as version 2. Existing unversioned and version 1 rules migrate without changing their identifiers, windows, enabled state, priorities or values. A list contains at most 100 distinct rules and 256 KiB of JSON; complete local settings also have a 256 KiB UTF-8 limit. Unsupported versions, duplicate identifiers, unsafe keys, unknown fields, malformed dates and invalid values are rejected before persistence. Schedule edits use the existing local settings history callback. Invalid edits leave the saved state and history unchanged.

The schedulable inventory includes language, independent English and Cantonese playfulness, dialog emoji, theme, density, seed color, font family, scale and weight, motion preference, display name, every narrator preference and every attention preference. Narrator and attention values are validated partial objects. Matching rules merge these objects by property, so a later voice selection does not erase an earlier rate preference. Credentials, access controls, protected mode state, personal vocabulary, and schedule management itself cannot be scheduled. Protected mode remains authoritative over effective language, playfulness, emoji and narration language; stored base choices remain recoverable.

Appearance and logo use `{ "version": 1, "reference": "local-snapshot-id" }`. These references select snapshots registered and validated locally by the owning appearance or logo consumer. They contain no image bytes, filenames, paths or credentials. The complete appearance snapshot preserves the owning editor's supported element states, layers, typography, colors, images, motion, palettes and inheritance. Custom logo data stays in its private local snapshot registry. An external source can select a known local reference but cannot inject a new image or appearance snapshot. Missing references produce an explicit failed application result and restore a prior temporary override where restoration is available.

`createScheduledCustomizationController({getBaseSettings, applySettings, appearance, logo, onError})` serializes temporary application. Each snapshot adapter supplies `resolve(reference)`, `applyTransient(snapshot)` and `clearTransient()`. `update(overrides)` returns per-consumer applied, restored, base, failed or restore-failed states. `dispose()` rejects future work, waits for the current application and restores the base. `applySettings` receives validated effective scalar and nested preferences and must apply them transiently. It must never persist these values over the user's base. Appearance and logo consumers must also preserve saved bases and history during temporary application. A false consumer verdict or thrown error is not reported as applied.

A rule selects every day with weekdays `[0,1,2,3,4,5,6]`, or an explicit distinct subset. Dates bound starting days inclusively. Time windows use the declared IANA timezone, start inclusively and end exclusively. Cross-midnight windows belong to their starting weekday and starting date. Equal start and end means the entire selected starting day. Both occurrences of a repeated daylight-saving wall time match; a missing wall time never occurs. Rules apply by increasing priority, then lexical identifier; the last matching value for each property wins. Empty rules or empty external settings apply no override. Outside matching windows, saved base preferences return.

API responses accept versions 1 and 2 with validated allowlisted `settings`. The renderer resolver requires a privileged adapter, discards stale refresh generations, clears removed or disabled source results, and drops results on failure or cancellation. The privileged adapter retains bounded HTTPS, DNS/address validation, no redirects, response-size and timeout limits, refresh throttling, and origin-bound Home Assistant credentials. Home Assistant `on` enables the rule's configured values; `off` leaves other rules or bases effective. Its credential never enters schedule data. See [the source contract](external-sources.md).

Focused checks cover migration, restart persistence, atomic rejection, per-property precedence, protected-mode suppression, source validation, cancellation, missing references, transient restoration, negative consumer results, timezone boundaries and daylight-saving behavior. These source-level checks do not establish a built interface, pixels, audio output, or native credential-vault availability.
