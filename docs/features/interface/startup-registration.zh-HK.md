# 啟動登記讀取確認

啟動偏好同作業系統啟動登記係兩個獨立事實。儲存偏好會經原生 login-item API 要求登記；狀態讀取真實登記，唔會假設已儲存偏好代表登記存在或已啟用。

## 含空格路徑

固定桌面執行環境版本 44.7.0 將傳畀 `getLoginItemSettings` 嘅查詢路徑當命令列解析。含空格而冇引號嘅執行檔路徑可能只匹配第一段，即使 `setLoginItemSettings` 已正確將完整引號路徑寫入 Windows Run 項目，仍會錯誤回報停用。行為見[上游修正](https://github.com/electron/electron/pull/54364)同[固定原生實作](https://github.com/electron/electron/blob/v44.7.0/shell/browser/browser_win.cc#L194)。

主處理程序只將 getter 執行檔路徑包喺一對引號內，並分開傳入準確 `--startup` 參數。驗證項目讀取同普通應用程式狀態都使用此正規化。Setter 路徑、登錄擁有權、已儲存偏好同原生啟用狀態結果保持原狀。無空格路徑同樣適用，亦唔會重複已有外圍引號。

## 驗證擁有權同恢復

驗證建立獨特名稱項目，只讀該項目，恢復原本不存在狀態時移除。絕不修改使用者其他項目。驗證名稱已存在時，任何修改前即停止。原生讀取為 false 或缺失仍屬失敗，唔會用已儲存偏好或成功假設代替。

須保留失敗封裝執行環境收據。修正後來源測試唔會令舊收據事後變成通過。聲稱執行時驗收前，須重建候選版本，經封裝設定控制重做實際啟用、停用同恢復，並涵蓋含空格執行檔路徑。恢復後確認獨特項目不存在。呢個驗證登記同讀取，唔係真實登入啟動。

## 聚焦檢查

執行 `node --test test/startup-verification.test.js`。Windows 上回歸會從 `CommandLineToArgvW` 取得解析結果，示範無引號路徑不符，再用正確引號登錄命令核對引號查詢。涵蓋有／冇空格路徑、準確參數同名稱、setter 輸入不變、啟用／停用／恢復、使用者項目保留同兩條讀取路徑。其他平台明確略過原生解析案例，唔證明 Windows 解析行為。
