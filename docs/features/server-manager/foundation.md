# Server manager foundation

This unit supplies authoritative Java version discovery, selected-version server-distribution metadata resolution, source-bound configuration descriptors, typed configuration controls, and an explicit four-target capability inventory. A separate internal local-process adapter now implements conditional creation and lifecycle operations; it is not wired into the product interface. No real server execution or license acceptance was performed during verification. Flavors, container and SSH targets, settings and plugins are described in the managed-server section below; existing-server adoption remains unavailable.

## Catalogue and provenance

`refreshJavaCatalogue` reads the complete official Mojang version manifest with a ten-second timeout, a four-MiB response bound, HTTPS origin restrictions and redirect rejection. Every returned version is retained, including historical channels. Duplicate identities, missing latest entries and untrusted metadata URLs are rejected. The snapshot records the exact source SHA-256 and retrieval time. `catalogueState` distinguishes current, stale, offline and unavailable snapshots. Offline never means current.

`resolveJavaDistribution` checks the selected version metadata against the manifest's SHA-1 before reading its dedicated-server entry. Missing server downloads are explicitly unavailable. Historical Java runtime requirements remain unresolved when official metadata omits them. A resolved download records URL, SHA-1 and size, but does not claim downloaded-byte verification, installation, runtime verification or EULA consent. A complete authoritative historical Bedrock distribution catalogue remains unavailable; current download pages cannot fill that gap.

## Configuration and target boundaries

Descriptors require edition, exact version, verified distribution SHA-256, authoritative source revision, help, permission, persistence consumer and live/restart semantics. Booleans map to switches, enumerations to searchable selectors, numbers to bounded numeric controls and text to text controls. The renderer accepts localized copy and a real action callback from its owner. Unknown extension data survives configuration patches unchanged; editing an unknown extension requires a real descriptor. A generic JSON or shell editor is not provided.

Local processes, local containers, SSH processes and SSH containers are independently inventoried with required identity and permission proofs. The local-process lifecycle has an internal conditional implementation but remains unavailable and unverified; the other three targets are implemented only by the managed-server service described below, and only against injected fakes in tests. Connection loss must never be represented as a stopped server.

## Internal local-process adapter

`LocalProcessServerAdapter` creates a new exclusive task-owned root, streams a bounded official distribution download, verifies exact size and SHA-1, records SHA-256, and publishes only verified bytes. Failed or canceled creation retains a durable non-ready state and owned staging for recovery. Existing roots are never overwritten. License state begins with `eula=false`; writing `eula=true` requires explicit consent bound to the exact server identity, version, distribution digest and official EULA URL. Fixture tests simulate this contract only, without accepting a real server license.

Launch remains unavailable by default: the trusted host must supply a verified compatible Java executable/digest and version-bound loopback configuration, supported property-schema and available-port proof. These services must come from real protected providers, never renderer-supplied self-attestation. After asynchronous approvals, distribution/runtime bytes are rechecked while a trusted native deny-write/delete file lease protects both exact files. This lease provider is unavailable by default and must retain real native handles until the owned process exits; a Boolean claim or a rehash alone is not atomic file pinning. No native lease implementation or guarantee was exercised by the fake-process tests. A failed lease release retains its ownership object, blocks fresh startup and records recovery-required state. Admission, release and persistence errors are aggregated; persistence is attempted even after release fails. A process error alone does not release its lease or discard the child object, and actual exit settlement releases at most once. Startup cancellation before publication leaves no configuration; a later canceled attempt records its generated configuration and permits a fresh attempt only when those owned bytes remain unchanged. Launch is shell-free and hidden. The JVM uses `-Xmx512M`; this is not a complete native-process memory/CPU job boundary. The default `windowsProcessIdentity` reads exact PID, creation time and executable path through a bounded native process query. The adapter also retains its own child-process object and fails closed on identity loss.

Normal stop writes only `stop` to the verified owned process, waits within a bounded timeout and never force-terminates it. Lifecycle state writes are serialized so an older running snapshot cannot overwrite a later exit. Process launch is not server readiness: readiness remains unverified. Restart/recovery adoption, complete resource/job limits, storage-capacity admission, full logs/status protocols, GUI licensing controls, native IPC/provider integration and real server acceptance remain pending. A new adapter session cannot silently adopt a persisted process or root. The other three targets are handled by the managed-server service below.

## Flavors, four targets, plugins and settings

The managed-server service in `src/main/server-targets-service.js` is separate from the verified-download preparation above. Its servers use their own identifiers, `managed-<uuid>`, and it is reached through the same host dispatch. It prepares, starts, stops, reports the status of, tails the logs of and cancels servers on all four targets: a local process, a local container, an SSH process and an SSH container. Every external process and network call is injected, so the tests use fakes.

Flavors: `src/features/server-manager/flavors.js` reads the official public APIs. These are the Mojang version metadata for Vanilla, `api.papermc.io/v2` for Paper, `api.purpurmc.org/v2` for Purpur, `meta.fabricmc.net/v2` for the Fabric server launcher, the Forge promotions file and `maven.minecraftforge.net` for Forge from Minecraft 1.18, and `maven.neoforged.net` for NeoForge. Requests are HTTPS only, restricted to exact hosts (redirects included), and bounded in size and time. Integrity is reported exactly as the source gives it: SHA-1 and size for Vanilla, SHA-256 for Paper, MD5 only for Purpur and labelled weak, a SHA-256 or SHA-1 sidecar checksum for Forge and NeoForge when one exists, and no digest at all for the Fabric launcher. When there is none, the result says `unverified-upstream` and the SHA-256 of the received bytes is pinned instead; nothing is described as verified that was not. Forge and NeoForge ship an installer, which is the verified file, and it is run once with the documented `--installServer` argument; the finished server itself is not independently verified.

Targets: a local process runs the system `java` with a memory limit and an ownership marker, `-Dmfe.server=<id>`, and a normal stop writes `stop` to the console and never kills the process. A local container runs through `docker` with an argument array, using either the official `itzg/minecraft-server` image, which downloads the flavor itself so the desktop cannot verify it and the result says `delegated-to-image`, or `eclipse-temurin` with the verified jar mounted read-only. Ports are published on `127.0.0.1` only, and stop and status act only on a container whose `mfe.server` label matches. An SSH process and an SSH container use the system `ssh` executable with argument arrays, `BatchMode`, `StrictHostKeyChecking=yes` and password authentication switched off, so a host key must already be trusted and a password is never used. The remote command is one string made from fixed templates with allow-listed, single-quoted values, the verified jar is streamed over the connection, and its remote SHA-256 must match the local one. The key file is chosen in a native file chooser; the main process keeps its path and the renderer sees only an opaque `key-<uuid>` and a file name. Without a key, the ssh-agent is used.

License: preparation writes `eula=false`. Start is refused until the person accepts the exact license in a native dialog, and only then is `EULA=TRUE` given to a container image.

Settings: `src/features/server-manager/server-properties.js` defines the editable keys with types and bounds, such as port, message of the day, maximum players, difficulty, game mode, online mode and view distance. RCON, the bind address, the level name and resource pack keys are not editable, and comments and unknown keys are preserved byte for byte.

Plugins and mods: `src/features/server-manager/extensions.js` uses `api.modrinth.com/v2` for plugins (Paper, Purpur) and mods (Fabric, Forge, NeoForge). A file is installed only when the API published a SHA-512, the download host is `cdn.modrinth.com`, the size is within 128 MiB and the received bytes match. A jar chosen in the native file chooser is installed with its locally computed SHA-256 and is marked as not verified against a publisher. Installing needs a stopped server.

Java requirement: when a server is prepared, `resolveJavaRequirement` in `src/features/server-manager/flavors.js` reads `javaVersion.majorVersion` from Mojang's version metadata and stores it with the server as `javaMajor` (with `javaSource` recording `mojang` or `table`). Paper, Purpur, Fabric, Forge and NeoForge all run a Mojang release and none of their public APIs publishes a stricter value, so Mojang's number applies to every flavor. If the metadata cannot be read, the documented release table in `requiredJavaMajor` is used, including Java 25 for year-based releases such as 26.1 and later, and the source is shown as `table`. Before every Start the desktop compares that number with the Java it would actually run: `java -version` on this computer for a local process, and `java -version` over SSH for an SSH process. If the Java is missing or too old, Start is refused before anything is launched, with a message that names the required and the found major in English, Cantonese or both. The refusal leaves the card `failed` with a reason chip such as "Needs Java 25", and a new enough Java clears it on the next Start. Container targets pick the image from the same number: the `eclipse-temurin` runtime image for a mounted jar, and the matching `itzg/minecraft-server` tag for the official image mode.

Failure states: a card never stays `running` after its server has gone. A local process reports its own exit at once. Containers are checked through `docker inspect` (state and exit code) and SSH processes through a pid liveness check, both polled every few seconds while any card is live, and a refresh of the state does the same check. A requested stop, or an exit with code 0 (for example the in-game stop command), becomes `stopped`. Any other end becomes `failed` with the exit code or signal when known, the reason in `errorCode`, and the last 20 log lines in `lastLines`, which the card shows under the reason chip. Starting a failed card again clears the failure.

Closing the window: a plain close hides the window and keeps the drive in the tray. When a managed server is `starting` or `running`, the close instead asks whether to keep running in the tray, stop servers and quit, or cancel, using `src/main/window-close.js`. Every outcome is visible and none is silently dropped. Quitting stops local process servers with the console `stop` command; container and SSH servers keep running after the desktop quits, and the dialog says so.

Interface: `src/renderer/features/server-manager/targets-panel.js` is the panel below the preparation controls. It has a target picker that shows real availability, flavor and version selects loaded only on request, state chips, logs, a settings form and plugin installation, in English, Cantonese or both, with the shared motion tokens and a reduced-motion fallback.

Verification: run `node --test test/server-targets-service.test.js test/server-flavors.test.js test/server-launch-plans.test.js test/server-properties-and-extensions.test.js test/server-managed-adapters.test.js test/server-targets-panel.test.js`. These tests use fake processes, Docker, SSH and network only. No real server, container, SSH host, Java runtime, Docker daemon or download took part, and the panel was not captured in a built application, so everything in this section is verified with synthetic fixtures only.

## Integration handoff

Import the catalogue module only into the trusted host layer, with explicit refresh and owned cache persistence. Never expose arbitrary fetch URLs to the renderer. Bind configuration descriptors to an actually verified distribution and generated/version-reviewed defaults before enabling editing. Mount `mountConfigurationControls` through the existing localized surface and supply the established permission, confirmation, persistence and history action. Registry/navigation, optional above-control guidance, complete documentation/help, structured collection controls, native IPC, licensing, runtime lifecycle, extensions and real rendered acceptance remain integration or subsequent implementation work. No shared registry or navigation files changed in this unit.

Run `node --test test/server-manager.test.js`. These tests prove source behavior and negative inventory/configuration checks; they are not installed-server or GUI acceptance.
