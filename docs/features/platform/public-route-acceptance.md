# Public route acceptance boundaries

This is a foundation inventory, not a completion report. Every listed route inherits all 104 canonical feature obligations. A mounted shared control, passing source test, historical capture, or successful installer does not establish browser acceptance. Advanced appearance and image editors, complete settings navigation, complete export formats, and advanced history remain incomplete.

## Route ownership

Home, the documentation library, category indexes, full articles, the wiki index, individual wiki articles, and the capture gallery mount the public document shell directly. The browser workspace owns its own shell. Preferences, local access, language, appearance, schedules, attention, private history, search builders, command palette, notifications, context menus and confirmation dialogs are individually accountable nested surfaces. The website provides documentation, visitor settings and verified downloads. Native drive management belongs to the installed application. Explicitly paired local tools use only their allowed mediation endpoints.

The companion machine-readable inventory enumerates every generated route and each canonical identifier. All browser verdicts remain unverified. Process and release obligations still require evidence from their actual route; their presence in this inventory does not make a browser responsible for producing an installer.

## Smallest real acceptance sequence

1. Build through the root entrypoint, pin the candidate and staging manifest, and compare served HTML, scripts, styles, workers and provenance with staged bytes before interaction.
2. Open the exact staged home in an isolated hidden browser. Check initial version and build provenance, closed palette and notifications, real tabs and groups, keyboard focus, context actions and restoration. Start with normal English/light and minimum-width bilingual/dark, then run the required language, theme, viewport and display-scale matrix.
3. Visit every inventoried route. Verify full article and wiki content, internal links, anchors and assets. Exercise the shared shell on each route family and every distinct nested surface. Search page content and settings through the regex builder, including invalid patterns and cancelled searches.
4. Register a synthetic local profile. Reject an incorrect password, unlock correctly, lock and reload. Verify encrypted credential records and independently passworded history. Change one setting and verify exactly one history entry; restore it through the actual UI. Profile-locked history actions must open a truthful unlock path or refuse without changing data.
5. Load a neutral wording file before and after authentication. Verify replace, persistence, clear, invalid input, lock restoration and local-only operation. Reset the profile in a second tab during pending encryption; the stale tab must not write an orphan cache.
6. Set language playfulness independently, confirm default 5, enable the protected mode from Cantonese and bilingual states through its credential flow, verify suppressed controls remain suppressed after navigation and reload, then reject an incorrect disable credential and accept the correct one. Imports, reset and history restore must not remove the credential requirement.
7. Navigate away and back through the browser cache. Controls must remain live while authentication and pending confirmations are cancelled. Drive exact confirmation text, both keys, sliders, emergency exit and abort through real dialogs. Inspect minimum-width overflow, focus order, zoom and accessible names, and retain genuine captures bound to source, staging hashes and privacy checks.
8. Keep source checks, staged-browser checks, installed native checks and live publication separate. Deployment acceptance additionally requires the live home, all route/assets, full article/wiki inventory and exact repository homepage readback.

## Evidence limits

No browser capture or live deployment is claimed here. Source tests cover selected composition and state transitions. The settings and editor audits maintain their own desktop and website columns. This feature introduces no HTTP API; a Postman collection is not applicable.
