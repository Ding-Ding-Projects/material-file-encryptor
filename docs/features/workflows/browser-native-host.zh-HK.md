# 瀏覽器原生訊息傳輸

`MaterialFileEncryptor.BrowserHost.exe` 為
`org.dingding.material_file_encryptor.downloads` 提供 Windows 原生訊息傳輸。
主機有兩種模式：由瀏覽器啟動時，先核對設定內允許嘅來源，再透過同用戶命名管道
轉送訊息；桌面程式以隱藏、自行管理嘅子程序啟動 `--broker`，經標準輸入輸出
交換有關聯編號同長度限制嘅訊息。傳輸層唔會開啟保管庫、處理檔案明文，
亦唔會將瀏覽器配對憑證儲存到磁碟。

正式管道名稱由目前 Windows 用戶嘅 SID 衍生。用戶端同伺服器都要求
`PipeOptions.CurrentUserOnly`。伺服器會讀返真實 DACL，只有當佢包含單一允許項目，
指定目前用戶嘅實際 SID，而且有讀寫權限，先會接受。權限缺失、範圍過大或者
不符合預期，代理程序會喺報告就緒之前停止。呢個檢查避免將部分 .NET 版本採用嘅
權杖擁有者 SID 當成實際用戶 SID。完整性或者提升權限層級不同，仍然可能令連線
失敗。支援路徑要求桌面程式同瀏覽器使用相同嘅一般用戶權限層級。

## 同意同下載狀態

擴充功能來源字串係允許清單資料，唔係瀏覽器身分證明。同一用戶執行嘅程序可以
手動啟動主機，亦可以連接該用戶嘅管道。因此每次新配對都要喺已解鎖嘅桌面程式
明確批准。同意畫面要指出所申請嘅來源，並解釋傳輸層無法驗證手動啟動嘅同用戶
程序。預設選項係拒絕。批准配對唔等於批准下載，亦唔等於批准目的地。

JavaScript 代理將配對同下載建議交畀 `createBrowserDownloadReceiver`。
工作階段只保留喺記憶體，15 分鐘後到期，每個工作階段最多接受 64 個不重複建議。
已接受建議只會轉送到主機專用 `receiveBrowserProposal` 方法，畫面程序無法呼叫。
原生目的地選擇器同明確「開始下載」動作仍然係獨立步驟。

擴充功能可以用精確嘅 `{type:"status",session,id}` 訊息查詢自己嘅建議。
代理根據真實桌面下載事件報告 `awaiting-confirmation`、`downloading`、`completed`、
`failed` 或 `cancelled`，以及位元組進度。關聯編號會以 `browserCaptureId`
保留喺佇列項目。狀態回覆唔包含目的地路徑、網址、明文或者憑證。
桌面鎖定時必須撤銷代理配對，離開時必須關閉自行管理嘅子程序。

`close()` 會即時撤銷接收權限，同時呼叫嘅用戶會共用同一份非同步收據。
喺三秒限時內，佢會觀察自行管理嘅程序離開、全部繼承標準輸入輸出串流關閉，
以及未完成回覆 callback 嘅狀態。收據包含 `processExited`、`stdioClosed`、
待處理要求／回覆數目同 `verified`。未觀察到程序離開、串流未清空，或者原生
同意仍未完成，`verified` 都會保持 false。唔會終止無關程序，亦唔會將發出終止
要求當成程序已離開嘅證明。
如果之前收據未核實，之後重試會重新觀察目前程序離開同清空狀態。
已成功完成嘅收據會保持不變。

桌面程式由綑綁 `browser-host` 目錄初始化 `createBrowserHandoffLifecycle`。
已審閱設定缺失或者無效時，代理程序唔會被建立。桌面隔離驗證模式亦會停用正式
代理，令合成測試同目前用戶流程分開。啟動接駁原生同意、解鎖／關閉接收限制、
主機專用建議傳送同下載事件。每次發佈已鎖定或者助手未核實狀態，都會撤銷配對。
離開、更新準備同驗證退出會先等到已核實關閉收據，先完成服務關閉。
`getState` 包含真實 `browserDownloadHandoff` 狀態同最後關閉收據。

啟動失敗處理器會喺 `app.exit(1)` 前使用相同已核實關閉界線。
收據未核實時，桌面程式保持運行、記錄需要恢復狀態，並提供原生「保持運行／
重試關閉」選項，預設保持運行。重試會重新核對同一自行管理程序同串流證據。
恢復對話框不可用時，程序亦會保留並報告未核實狀態。
啟動失敗唔代表可以遺下未核實代理程序。

一般桌面功能 IPC 有獨立存取 context 界線：主程序核實要求 frame 後，會將真實
`event.senderFrame` 作為第四個原生服務參數傳送。主程序管理嘅 frame getter
回傳 `window.webContents.mainFrame`。畫面 payload 唔可以提供 actor，loopback
adapter 呼叫會保持缺少 context，唔會借用目前畫面 frame。
存取 adapter 必須拒絕缺少 context 嘅要求。原生下載建議繼續用主機專用路徑，
唔會捏造畫面存取身分。

## 身分同登記計劃

`scripts/browser-native-registration.mjs` 接受已審閱嘅 CRX3 套件，以及第 1 版
公開身分收據。收據包含 `format`、`signatureVerified`、`extensionId`、
`publicKeyDerBase64`、`packageSha256` 同 `publicKeySha256`。
程式會獨立核對套件同公開金鑰雜湊、由公開金鑰衍生擴充功能 ID、檢查 CRX3
已簽署身分，並核實涵蓋已簽署標頭同內容嘅對應 RSA 或 ECDSA 簽章。
單靠收據寫住成功唔會通過驗證。未簽署嘅原始碼套件唔會被接受。

產生器亦要求已正規化嘅絕對安裝主機路徑同資訊清單路徑。佢會輸出原生主機
資訊清單、`browser-host-config.json`，以及 Chrome 同 Edge 嘅精確 HKCU 登記計劃。
佢唔會執行登記指令、安裝或者移除主機、改動瀏覽器設定檔，亦唔會開啟用戶瀏覽器。
已有輸出檔案會保留，唔會被覆蓋。未有已審閱套件身分時，原生交接保持不可用。
唔會將佔位擴充功能 ID 當成可信身分出貨。

建置將執行檔編譯到 `out/browser-host`，封裝要包含該目錄，以及存在時已核實嘅設定。
主機沿用現有未簽署 Squirrel.Windows 封裝路徑。編譯或者綑綁傳輸層唔會證明
已安裝呼叫者可信、主機登記成功、擴充功能已發佈、已安裝更新成功，或者移除成功。
實際安裝同已安裝更新／移除流程仍然延後。

`build.bat /s /browser-host-only` 係此傳輸層嘅聚焦正式建置入口。
佢會執行現有相依項目啟動同詞彙檢查、發佈真正獨立 Windows 執行檔，並將原始碼
同執行檔雜湊記錄到 `out/evidence/browser-host-build.json`。
佢唔會封裝或者安裝桌面程式。完整 `build.bat /s` 路徑會喺封裝前發佈同一主機。

## 狀態範圍

兩個唯讀範圍跟足已核准嘅瀏覽器對桌面通道設計入面嘅「狀態」批准模式：
`read-lock-state` 同 `read-update-state`。兩個都要求同一條原生連線有有效、
仍然生效嘅配對，唔會喺桌面彈出提示，而且只回答固定嘅非機密欄位。處理者係
`src/main/browser-status-mediation.js`，讀取任何嘢之前，會先拒絕未知欄位、
原型花招同錯誤類型。

- `read-lock-state` 回傳 `lock-state`，`state` 係 `unlocked`、`locked` 或
  `unavailable`。桌面鎖定會撤銷所有配對，所以已配對嘅呼叫者通常見到
  `unlocked`；鎖定之後第一個要求會失敗，呼叫者亦會變返未配對。未配對嘅
  呼叫者永遠唔會知道鎖定狀態，因為佢收到嘅拒絕同其他未配對要求一樣。
- `read-update-state` 回傳 `update-state`，包含 `desktopVersion`、
  `availableVersion`（或者 `null`）、`phase`（`idle`、`checking`、
  `downloading`、`ready` 或 `unavailable`），以及 0 至 1 之間或者 `null` 嘅
  `progress`。階段取自真實嘅更新服務狀態。更新服務唔會回報下載位元組數，
  所以下載中 `progress` 係 `null`，更新暫存完成後係 1。答案入面唔會抄入
  任何網址、標籤、提交、路徑或更新來源細節。

兩個答案都喺現有 64 KiB 訊框同 35 秒要求期限之內。唔會儲存任何嘢，亦唔會
發出授權。

## 確認範圍：focus-authenticator

「確認」批准模式嘅第一個範圍係 `focus-authenticator`。已配對來源只會傳送
`{type:'focus-authenticator', session}`。已解鎖嘅桌面隨後會顯示原生 Material
確認提示，呢個係由主程序擁有嘅強制回應視窗，瀏覽器同應用程式畫面都冇辦法代答。
提示會用目前介面語言（英文、廣東話或者雙語）寫明要求來源、操作同確切目標。
「拒絕」係預設按鈕，按 Escape 亦代表拒絕。處理者係
`src/main/browser-confirm-mediation.js`，提示文字喺
`src/main/browser-confirm-prompt.js`。

- 批准之後，桌面會將視窗移到前面並開啟驗證器檢視。答案係 `authenticator-focused`，
  `schemaVersion` 為 1，`state` 係 `shown`、`rejected`、`busy` 或者
  `unavailable`。答案永遠唔會包含驗證碼、帳戶名稱、機密或者路徑。
- 同一時間最多只有一個待回答提示。已有提示等緊回答時，第二個要求會得到
  `busy`，唔會排隊。
- 桌面已鎖定、視窗隱藏或者縮到系統匣、桌面正在關閉、驗證模式，或者組建冇提供
  原生批准回呼，都會即時回答 `unavailable`，永不排隊。冇原生批准回呼，
  任何程序都冇辦法完成呢個範圍。
- 鎖定、中斷連線、離開同更新準備都會將待回答提示當作拒絕撤回，要求隨後因為
  配對已經冇咗而失敗。單單拒絕一次唔會撤銷配對。

## 學校模式範圍：read-school-mode 同 set-school-mode

兩個範圍令已配對嘅擴充功能可以查看，同要求更改桌面嘅學校模式。設定由桌面擁有：
佢存放喺共用模式紀錄 `shared-settings.json`，擴充功能本身冇自己嘅學校模式。
兩個範圍都由 `src/main/browser-school-mediation.js` 處理。

- `read-school-mode` 係「狀態」範圍。已配對來源只會傳送
  `{type:'read-school-mode', session}`，唔會出現提示。答案係 `school-mode`，
  `schemaVersion` 為 1，帶有布林值 `enabled` 同模式目前嘅顯示 `name`。名稱係最多
  80 個字元嘅純文字，控制、分隔同格式字元（包括雙向覆寫）都會被移除；如果冇剩低
  可讀內容，就會用預設名稱。未配對嘅呼叫者會得到慣常嘅拒絕，紀錄讀唔到時要求會
  失敗，而唔會估。
- `set-school-mode` 係「重新驗證」範圍。已配對來源只會傳送
  `{type:'set-school-mode', session, enabled}`，`enabled` 為布林值。已解鎖嘅桌面
  隨後會即時做一次原生身份檢查：由主程序擁有嘅設定檔驗證對話框，你要喺桌面輸入
  現有嘅保險庫密碼。呢個組建唔使用 Windows Hello，因為儲存庫入面冇 Windows Hello
  整合。密碼喺原生層檢查，永遠唔會去到瀏覽器、擴充功能或者中介模組。檢查成功之後，
  桌面先會寫入設定，而且用同桌面個人化畫面一樣嘅共用紀錄寫入器，亦會同桌面上更改
  一樣通知已開啟嘅視窗。
- 答案係 `school-mode-set`，`schemaVersion` 為 1，`state` 係 `changed`、
  `unchanged`、`rejected`、`busy` 或者 `unavailable`，另有 `enabled`，即桌面目前嘅
  開關狀態，讀唔到時為 `null`。答案唔包含憑證、設定檔資料或者路徑。
- 呢個提示同「確認」模式共用：兩者加埋最多只有一個待回答提示，第二個要求會得到
  `busy`，唔會排隊。桌面已鎖定、視窗隱藏或者縮到系統匣、桌面正在關閉、驗證模式，
  或者組建冇提供驗證回呼，都會即時回答 `unavailable`。冇原生回呼，任何程序都冇辦法
  更改設定。未回答嘅提示會喺 30 秒後、主機期限之前當作 `rejected` 撤回；鎖定、
  中斷連線、離開同更新準備亦會撤回。單單拒絕一次唔會撤銷配對。
- 已開啟而且有自己本機憑證保護嘅模式，只可以喺檢查嗰個憑證嘅桌面關閉：瀏覽器要求
  會得到 `rejected`，紀錄原封不動。開啟模式，或者關閉冇記錄本機憑證嘅模式，只需要
  保險庫密碼檢查。

## 元素鎖範圍：read-element-locks 同 set-element-lock

兩個範圍令已配對嘅擴充功能可以查看，同要求桌面更改自己工作區分頁嘅鎖。每一個鎖都
由桌面擁有：佢哋存放喺桌面自己元素鎖用嘅同一類受保護 `element-lock:` 紀錄，身分係
`extension:connection`、`extension:personalization`、
`extension:changelog`、`extension:notes`、`extension:docs`、`extension:support`、
`extension:dimsum`、`extension:models` 同 `extension:status`。呢份固定清單，每個選項
分頁一項，放喺 `src/shared/extension-lock-targets.js`；擴充功能保留一份一模一樣
嘅副本，並有測試比對兩者。其他目標一律喺做任何嘢之前就被拒絕。傳輸由
`src/main/browser-element-lock-mediation.js` 負責，紀錄處理喺
`src/main/access-integration.js`。

- `read-element-locks` 係「狀態」範圍。已配對來源只會傳送
  `{type:'read-element-locks', session}`，唔會出現提示。答案係
  `element-locks`，`schemaVersion` 為 1，加上 `locked`，即係目前有紀錄嘅分頁編號清單，
  次序固定。唔會返回紀錄內容、因素細節或者路徑。
- `set-element-lock` 係「重新驗證」範圍，鎖定同解鎖都適用。
  已配對來源只會傳送
  `{type:'set-element-lock', session, target, locked}`，`target` 係已審核嘅分頁編號，
  `locked` 為布林值。已解鎖嘅桌面隨後會即時做原生人身檢查：由主程序擁有嘅設定檔驗證
  對話框，你要喺桌面輸入現有嘅保險庫密碼。呢個版本唔使用 Windows
  Hello，因為儲存庫入面冇 Windows Hello 整合。密碼永遠唔會去到瀏覽器、擴充功能或者中介模組。
  檢查成功之後，桌面先會寫入或者移除紀錄。
- 答案係 `element-lock-set`，`schemaVersion` 為 1，`state` 係
  `changed`、`unchanged`、`rejected`、`busy` 或 `unavailable`，加上 `target` 同
  `locked`，即係桌面對嗰個目標嘅目前狀態，讀唔到就係 `null`。答案唔包含憑證、紀錄或者路徑。
- 鎖定會寫入單一因素嘅密碼鎖，驗證器係本機設定檔驗證器嘅副本，所以你用現有嘅保險庫密碼
  就開到，亦唔會產生新秘密。已有嘅鎖永遠唔會被取代
  （`unchanged`），冇可用本機設定檔嘅鎖定會得到 `rejected`。
  解鎖只會移除仍然係單一因素密碼鎖，而且同目前設定檔驗證器吻合嘅紀錄。較強嘅政策、用
  另一個密碼嘅鎖，或者之後已更改嘅設定檔都會得到 `rejected`，紀錄原封不動，所以只可以喺
  桌面移除。寫入使用受保護儲存庫嘅修訂檢查，所以同時更改會得到 `rejected`，而唔會被覆寫。
- 提示同確認模式同學校模式共用：三者之間最多只有一個等待中，第二個要求會得到 `busy`，
  唔會排隊。已鎖定嘅桌面、隱藏或者縮到系統匣嘅視窗、正在關閉嘅桌面，或者冇驗證回呼嘅
  組建，會即時得到 `unavailable`；冇原生回呼，任何程序都無法更改或者移除鎖。
  冇人回答嘅提示會喺 30 秒後以 `rejected` 撤回，早過主機嘅期限，而鎖定、中斷連線、離開
  同更新準備都會撤回佢。單單被拒絕唔會撤銷配對。

桌面自己嘅畫面唔會顯示或者執行 `extension:` 紀錄，因為冇桌面控制項帶有呢啲身分。
紀錄係桌面對擴充功能必須保持鎖住嘅長久聲明；呢條路徑移除唔到嘅紀錄，目前要喺桌面端
經受保護紀錄儲存庫處理，仍未有對應嘅桌面畫面。

## 解鎖階梯範圍：read-unlock-ladder 同 request-unlock-step

兩個範圍令已配對嘅擴充功能睇到桌面本機設定檔喺解鎖階梯嘅位置，並要求下一步。階梯、
共用冷卻同每一個挑戰都由桌面擁有。傳輸層係
`src/main/browser-unlock-ladder-mediation.js`；桌面狀態經 `src/main/access-integration.js`
嘅 `readNativeWaitingLadder` 讀取，佢會向 `src/main/access-challenges.js` 現有嘅存取
狀態機查詢設定檔目標。

呢個組建入面階梯到底係乜，對理解範圍好重要。有序級別係桌面對設定檔憑證嘅升級級別：
每輸入五次錯誤憑證加一級，每級將共用等候時間由 30 秒起逐級加倍，去到第 8 級就達到一
小時上限。所以公開階梯有九個 id，`level-0` 至 `level-8`，任何更高嘅儲存級別都讀作
`level-8`。輸入正確憑證會清除升級。桌面嘅等候挑戰（揀點心、算術同鼴鼠回合）由桌面視窗
嘅渲染器回答；主程序冇可以執行挑戰嘅入口，呢條路徑亦冇自行發明一個。

- `read-unlock-ladder` 係狀態範圍。已配對來源傳送剛好
  `{type:'read-unlock-ladder', session}`，唔會出現提示。答案係 `unlock-ladder`，載有
  `schemaVersion` 1、`level`（目前級別 id）、`levels`（有序 id）、`cooldownUntil`
  （共用冷卻完結時間，以紀元毫秒計；冇冷卻進行中就係 `null`）同 `recovery`（`none`、
  `available` 或者 `required`）。唔會返回憑證、挑戰、答案、失敗次數或者路徑。桌面對
  設定檔憑證冇復原流程，所以呢個組建入面 `recovery` 永遠係 `none`；保留呢個欄位係令
  擴充功能日後顯示新狀態時毋須改協定。
- `request-unlock-step` 係重新驗證範圍。已配對來源傳送剛好
  `{type:'request-unlock-step', session}`。答案係 `unlock-step`，載有 `schemaVersion`
  1、`state`（`advanced`、`cooldown`、`complete`、`rejected`、`busy` 或者
  `unavailable`）、桌面報告嘅 `level`（或者 `null`）同 `cooldownUntil`。
- 進行中嘅冷卻只會被報告，永遠唔會被繞過：答案係 `cooldown`，唔會顯示提示，亦要等冷卻
  完結先會試憑證。冇升級就冇嘢可以爬，答案係 `complete`，同樣冇提示。
- 只有冷卻已完結而仍然記錄住級別，已解鎖嘅桌面先會對當事人做一次新鮮嘅原生檢查：
  由主程序擁有嘅設定檔驗證對話框，當事人喺桌面輸入現有嘅保險庫密碼。呢個組建唔使用
  Windows Hello，因為儲存庫冇 Windows Hello 整合。密碼永遠唔會去到瀏覽器、擴充功能
  或者中介模組。憑證正確時，桌面自己嘅狀態機會清除升級，模組跟住再讀取一次狀態。
  只有讀返嚟嘅級別低過之前，先會報告 `advanced`；檢查後級別冇變就係 `rejected`，之後
  讀取失敗就係 `unavailable`，錯誤憑證就係 `rejected`，並附上桌面而家報告嘅級別同冷卻，
  當中可能包括今次錯誤嘗試開始嘅冷卻。
- 提示同確認模式、學校模式同元素鎖共用：四者之中同一時間最多一個等待中，第二個要求
  會得到 `busy`，唔會排隊。已鎖定嘅桌面、隱藏或者縮到系統匣嘅視窗、正在關閉嘅桌面，
  或者冇驗證回呼嘅組建，會即時得到 `unavailable`；冇原生回呼，任何程序都無法推進階梯。
  冇人回答嘅提示會喺 30 秒後以 `rejected` 撤回，早過主機嘅期限，而鎖定、中斷連線、離開
  同更新準備都會撤回佢。單單被拒絕唔會撤銷配對。

所以呢條路徑唔會將桌面嘅等候挑戰帶去瀏覽器，亦唔會畀瀏覽器回答任何挑戰，更加唔會縮短
冷卻。佢做得到嘅，只係喺冷卻完結之後，畀當事人喺桌面證明保險庫密碼，從而清除已記錄
嘅升級，而桌面自己嘅登入同樣會做到呢件事。

設計入面各範圍嘅狀態：`read-lock-state`、`read-update-state`、
`focus-authenticator`、`read-school-mode`、`set-school-mode`、
`read-element-locks`、`set-element-lock`、`read-unlock-ladder` 同
`request-unlock-step` 已經喺主程序同擴充功能實作；
`read-profile-summary` 由受保護中介處理；設計入面其餘候選範圍尚未實作。學校模式、
元素鎖同解鎖階梯範圍只用合成測試資料、假原生代理，以及（紀錄同階梯狀態方面）真實嘅
存取狀態機加上原生保險庫檢查嘅替身驗證，冇真實桌面對話框、已安裝組建、
真實瀏覽器登記或者已擷取提示參與，所以未經端到端驗證，包括瀏覽器要求更改學校模式之後
已開啟桌面視窗嘅重繪、桌面鎖定畫面會否顯示擴充功能紀錄，以及桌面解鎖畫面會否毋須重新
載入就反映經呢條路徑清除嘅級別。

## 配對代碼：begin-qr-pairing

維護者喺 2026 年 10 月 14 日將 `begin-qr-pairing` 由「配對手機」改為「用二維碼配對
瀏覽器」。佢喺現有 `pair` 訊息加一個可選證明，唔會取代原生批准提示；每次配對
仍然必須批准。

- **顯示代碼。** 已解鎖嘅桌面有「配對瀏覽器」分頁，內有「顯示配對代碼」按鈕。
  主程序發出代碼，分頁用現有二維碼編碼器同時顯示文字同二維碼。二維碼只載有代碼
  本身，冇網址，亦冇其他內容。按「隱藏配對代碼」、兩分鐘到期或者關閉分頁都會清除。
- **代碼。** 8 個字元，來自 `ABCDEFGHJKMNPQRSTUVWXYZ23456789`（冇 `0`、`O`、
  `1`、`I`、`L`），用 `crypto.randomInt` 產生。有效 2 分鐘，只可使用一次。
  同一時間只得一個有效代碼，再顯示新代碼會取代舊代碼。桌面鎖定、正在關閉、
  準備更新，或者原生接收程式未運行時，唔會發出代碼。鎖定、結束、準備更新同
  關閉接收程式都會清除代碼。代碼只存喺記憶體，唔會寫入記錄、通知、儲存空間或回覆。
- **使用代碼。** 擴充功能可以送出 `{type:"pair",code}` 取代 `{type:"pair"}`。
  其他額外欄位仍然會被拒絕。喺顯示任何提示之前，會用固定時間比較將所提供代碼
  同唯一有效代碼對照。錯誤、過期、已用過或者未發出嘅代碼，直接拒絕而唔顯示提示。
  連續五次錯誤會清除有效代碼。冇 `code` 嘅 pair 訊息跟原有流程，毫無改變。
- **批准。** 代碼吻合時提示仍然會出現，預設仍然係「拒絕」，並加一句說明擴充功能
  輸入咗呢部桌面顯示嘅代碼。拒絕唔會用掉代碼，代碼直至到期都仍然有效；批准就會
  用掉。提示開啟期間代碼如果改變，配對會被拒絕。
- **身分。** 配對後，擴充功能經現有 `read-update-state` 範圍讀取桌面版本，並喺
  「已與呢部桌面配對」旁邊顯示。我哋冇虛構身分資料：版本只係標籤，唔係證明。

`test/browser-pairing-code.test.js` 涵蓋字元集、密碼學來源、到期、取代、單次使用、
連續五次錯誤重設、永遠唔會到達提示嘅拒絕路徑、批准仍然必需、批准後用掉代碼、
鎖定同關閉時清除，以及回覆從不帶有代碼。`test/browser-pairing-view.test.js` 用
替身文件檢查桌面分頁，並解碼二維碼證明內容正正係代碼。以上都係合成測試資料：
冇已安裝嘅桌面、冇真實原生訊息登記，亦冇用真實鏡頭掃描真實二維碼，所以端到端
路徑未驗證。

## 限制同驗證

全部傳輸訊息使用四位元組小端序長度、嚴格 UTF-8 JSON，以及 64 KiB 上限。
空白、過大、截斷、重複欄位同不安全原型欄位輸入都會被拒絕。
代理最多接受兩個連線用戶端，每個連線最多 256 個要求。
子程序啟動限時五秒，已連接要求限時 35 秒。傳輸診斷唔會包含訊息內容或者
工作階段值。

`test/browser-native-host.test.js` 驗證即時簽署嘅合成 CRX3 測試資料、簽章竄改、
收據不符、路徑拒絕、明確同意、未知欄位、重播同工作階段到期、來源允許清單、
三個流程狀態、有關聯編號嘅子程序訊息，以及過大輸入拒絕。
原生執行檔嘅 `--self-test` 路徑驗證訊息拒絕同獨立自行管理嘅同用戶管道，
包括真實 ACL 讀回同訊息往返。呢啲測試唔會接觸真實保管庫、已掛載磁碟機、
瀏覽器設定檔、登錄項目或者安裝。已安裝瀏覽器行為同三個可見桌面畫面，
要有另外嘅真實已安裝證據，先可以聲稱已驗證。

此聚焦傳輸實作已通過精確正式建置入口同 10 個原生合成檢查。
向 JavaScript 測試提供該建置嘅 `MFE_BROWSER_HOST_EXE` 時，14 個測試全部通過，
冇略過。編譯主機測試將主機複製到全新自行管理嘅測試目錄，只加入產生嘅合成設定，
以隱藏模式啟動兩個真實轉送程序，核實明確配對、建議、等候／下載中／完成狀態
同重播拒絕，然後關閉自行管理嘅程序並移除測試目錄。
呢啲係傳輸同通訊協定結果，唔係已安裝瀏覽器或者可見桌面驗收證據。
