# Documentation browser and status integration

## Documentation

### Independent surface delivery inventory

`contracts/surface-registry.json` supplements the historical two-surface assessment in `contracts/feature-delivery.json` without changing its verdicts or source bindings. The concrete registry includes publication home, library, wiki, gallery, generated articles and category indexes; publication preferences for each page; browser workspace views and bundled documents; desktop views, dialogs and bundled documents; and the extension popup. Every surface inherits the same 105 semantic declarations, but no completion verdict. Empty independent proof maps expand to unverified assessments.

`discoverFeatureSurfaces(root)` reads the publication catalogue and its actual article route function, workspace declarations, desktop declarations, and recursive documentation catalogue. `validateSurfaceRegistry(registry, expectedSurfaces)` requires that authoritative discovery result and rejects missing routes, mismatched route/component identities, duplicate surfaces, omitted families, inherited verdicts and borrowed proof. An implemented assessment needs its own exact route and selector, source commit, built hash and declared visual/interaction evidence. These are structural declarations, not verification that evidence exists or that a runtime check passed. The inventory is an acceptance backlog, not a claim that all required behavior ships.

Run `node --test test/feature-delivery-surfaces.test.js test/documentation-platform.test.js` for the bounded inventory checks. When a source article is added, removed or renamed, regenerate the registry from discovery before accepting its route inventory. The build and live publication remain separate acceptance work.

The handwritten required surface list independently requires exact vault and confirmation dialog identities, the dynamic restore-descendants dialog, all five personalization panels and its Home Assistant credential dialog, and access profile, locks, authenticator, support, history, unlock, waiting, wizard, confirmation and QR preview children on desktop and browser workspace hosts. Dynamic selectors that describe activation state are semantic ownership descriptors, not claims that the DOM exposes a stable CSS ID. Quoted HTML IDs are parsed within a single bounded opening tag. A dedicated regression removes the vault from both registry and extractor output, so correlated omission still fails.

`buildDocumentationCatalog(root)` reads every Markdown file under `docs/`, including the wiki, plus available root project articles. Each document records its full source text, stable path-based ID, category, headings and content hash. Symbolic links are excluded. Run `node src/features/documentation/build-catalog.mjs <repository-root> <output.json>` during packaging, then supply the parsed bundle to `mountDocumentation`.

`mountDocumentation(host, { catalog, translate, onExport, initialId })` provides article navigation, full-text search with the existing bounded worker-based regular-expression builder, heading anchors, internal Markdown links and Markdown export. The DOM-only renderer supports tables, fenced code, emphasis, lists and task lists, quotes, local raster images, and the exact attribute-free details/summary containers used in project articles. Arbitrary source HTML is rendered as text, not executed. External links accept HTTP and HTTPS only and are explicitly marked. Missing internal articles and anchors are displayed without an active link. The catalog must be regenerated after documentation changes; packaging integration remains required.

Image references are resolved against their owning article and included as data URLs only when they resolve to local PNG, JPEG, GIF or WebP files within the repository. Each file is limited to 5 MiB. SVG, remote images, path escapes, unsupported files and missing images display an unavailable state rather than making an unexpected network request. Each accepted asset records its original path and SHA-256.

`parseChangelog(markdown)` exposes dated version sections. The separate `mountChangelog(host, { entries, translate, onExport })` module adds date and category filters, bounded regular-expression search and filtered Markdown export. The host supplies categories when its changelog source has them. Undated sections remain visible without date filters and are excluded when a date bound is active.

## Status

`createApplicationStatus` is a trusted-process adapter around the supplied official status client factory. It never implements transport or credential storage. The host must import the shipped client, supply its process configuration, call `checkpoint` for meaningful updates and `finish` at exit, and expose only `snapshot()` over IPC. The snapshot uses an allowlist without credentials, session keys, repository paths or raw server diagnostics. `mountStatus` accepts a `getStatus` callback and reports configured, unavailable and read-failure states without claiming that a configured client has successfully published.

No enrollment secret is collected by the renderer. A missing factory is `CLIENT_NOT_CONFIGURED`. Live publication, authentication, startup/exit wiring, reply interactions and complete status-client contract verification remain unverified until the host integrates the adapter.

## Delivery inventory

`contracts/feature-delivery.json` lists canonical feature identifiers independently for desktop and site. Missing rows remain explicit and do not imply completion. An `implemented` row requires existing implementation, documentation, localization, tests and evidence paths. `validateFeatureDelivery` rejects omitted or duplicated rows and incomplete implemented claims. The separately checked-in required identifier list prevents discovery from silently hiding an omitted feature.

## Enforced inventory validation

`validateFeatureDelivery(manifest, exists?)` is an offline structural check. It enforces the independent required ID list, exactly one desktop and site row per ID, declared scope semantics, bounded nonempty reasons, safe bounded path arrays including persistence, and full commit IDs for every referenced path. A missing implementation never grants a scope exemption. An optional existence callback may inspect local files; its absence never implies that Git objects were checked.

`verifyFeatureDeliveryReferences(manifest, { repositoryPath, timeoutMs, totalTimeoutMs })` additionally uses the Git CLI to require each recorded commit/path to resolve to a blob. Commands are bounded to ten seconds each and the run to sixty seconds. Missing repository access or an expired overall deadline returns `referenceVerification: unverified`; absent recorded files return `failed`. Offline bundles should use structural validation and preserve this unverified source-existence boundary. A shallow clone may require fetching the recorded review commits before the repository-aware check can pass. Neither result proves built behavior or visual evidence.

## Wiki page identity

The aggregate wiki uses each validated source basename for its section identity, including `wiki-Home` and `wiki-CLOSEOUT_PROMPT`. Nested heading IDs and same-page fragment links use that same page prefix. Two complete pages may share a title without colliding or losing content. The original Markdown headings and raw-byte source hashes remain unchanged. The regression fixture renders two pages with matching headings, checks distinct IDs and every local fragment target, and verifies both complete headings remain present.

## Honest monetization audit

The product is free, and `scripts/audit-monetization.mjs` keeps it that way. `node scripts/audit-monetization.mjs` scans the desktop renderer, main process and shared code, the browser extension and the documentation website sources, skipping bundled third-party trees, fonts, icons and licence texts. It reports payment SDKs and payment hosts, card-number style fields and payment forms, purchase and upgrade wording, license-key and entitlement checks, trial timers, donation and review requests, and price tags. It also rejects payment dependencies in `package.json`, payment permissions and payment hosts in the extension manifest, and payment hosts inside any Content-Security-Policy. The exact sentences that state the product is free are the only allowed exceptions. The audit also requires a plain price statement, in English and Cantonese, on the desktop (Help, in a Material list control that enters with the shared Material motion), the extension options page and the website home page.

`test/monetization-audit.test.js` runs the audit against the real tree and requires zero findings. It also plants a violation of every kind in memory and in a temporary tree, and requires each to be reported, so the audit cannot silently pass by matching nothing. The pattern lists are documentation of the rule as much as code: widen them when a new payment mechanism appears, and keep the allowed free statements in step with the wording on the surfaces.

## README tabs and the human-time estimate

The README opens with a compact index (what the project is, the install line, the price statement and a contents list) and folds every long reference section into a `<details>` block with a descriptive `<summary>`. First-reader content is never collapsed, and the screenshot gallery keeps its own groups. `CONTRIBUTING.md`, `SECURITY.md`, `CODE_OF_CONDUCT.md` and `LICENSE` stay real files so GitHub shows them as tabs above the README.

The README section named "Project size and human-time estimate" is generated by `scripts/human-time-estimate.mjs`. It lists the tracked files with `git ls-files`, counts non-blank lines of hand-written code in five buckets (application source, the native engine, styles and markup, tests, and build and tooling scripts), and leaves out vendored and bundled trees, fonts, lockfiles, minified files, binaries, JSON data, design reference prototypes and Markdown prose, naming each exclusion. The native engine counts at 1.5 times its size. The result is divided by 25 to 50 lines per working day and 20 working days per month, which gives a range, labelled as an estimate with its arithmetic shown. `node scripts/human-time-estimate.mjs --write` refreshes the section and `node scripts/human-time-estimate.mjs --check` fails when it is more than 10 percent away from the current tree or its own arithmetic is wrong. `test/readme-tabs-and-estimate.test.js` enforces both the README structure and the estimate.
